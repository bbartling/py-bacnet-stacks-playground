# Day 111 — Verify source, image and hardware separately

[Previous: Day 110](day110.md) · [Course index](INDEX.md) · [Lab guide](LAB_GUIDE.md) · [Next: Day 112](day112.md)

**Week 16 · 45–90 minutes.** Prerequisites: Days 1–110, or equivalent skills. Reuse your earlier work rather than start every tool again.

## Goal

Implement the bounded change and collect the right evidence for its scope.

## Before you start

Read-only repository study first; software lab and optional isolated Pi/RS-485 bench. Follow the destination repository contract before edits. Follow [workspace and evidence conventions](LAB_GUIDE.md). Save today's work as `student-work/day111/` or in your own learning repository. Record the toolchain; commands and dependency behavior may differ across OS releases. Complete the baseline before the stretch.

## Concept

Validation should follow the changed boundary. Unit tests can prove parsing policy; topology tests prove software forwarding paths; an exact image adds packaging, service and runtime differences; physical hardware adds drivers and timing. QEMU is valuable but cannot certify an RS-485 trunk. The destination repo may require more checks than the course examples, and its actual instructions govern contribution work.

## Tiny example

Build an evidence table with columns `check`, `revision/image`, `environment`, `command`, `result`, and `artifact`. Use `not run` when a prerequisite is absent; do not merge that with pass.

Use this to explore the mechanism. It is deliberately smaller than the assignment.

## Coding challenge

- Implement the smallest change that passes the failing check and run all checks required by the destination repository for the touched scope.
- Review the diff for unrelated edits, changed defaults and undocumented capability claims.
- Study the Buildroot/QEMU/Pi path and run an available relevant image gate only when prerequisites and authorization are satisfied; leave physical validation pending when unavailable.

## Experiment

Rerun the original failure scenario on the changed code and compare the exact observed difference. Avoid broad performance claims from a single run.

Write your prediction before running the experiment, then record what changed and why. Use the [capture guide](lab-scripts/wireshark_filters.md) when packets are involved; for offline work, preserve input bytes and actual output instead.

## Acceptance checks

- The original problem is resolved by evidence rather than only compilation.
- Source, image and hardware rows are separate.
- No untested baud or image is labeled supported.

## Optional Python companion

Optional external oracle follows the existing repo gate; no appliance Python dependency is added.

## Stretch and reflection

What could still fail after a host-source test passes but before the same change is deployed in an image?

Save the source, relevant test output, and a short explanation of one failure you understand better now. Consult [this week's primary references](SOURCES.md#week-16) for exact API and protocol details. Live interop and hardware steps are learner-run labs, not results claimed by this document.

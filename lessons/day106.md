## Goal

Build a current map of the DIY router before changing any code.

## Before you start

Read-only repository study first; software lab and optional isolated Pi/RS-485 bench. Follow the destination repository contract before edits. Follow [workspace and evidence conventions](LAB_GUIDE.md). Save today's work as `student-work/day106/` or in your own learning repository. Record the toolchain; commands and dependency behavior may differ across OS releases. Complete the baseline before the stretch.

## Concept

The appliance combines Rust data-plane integration, management services and a Linux image. Source tests, host-built lab runs, QEMU image tests and physical flashed-device tests establish different facts. README claims can become stale; use the current gate ledger and evidence paths. A course milestone is not permission to check every product checkbox. Begin with read-only study and identify one bounded question.

## Tiny example

In `/home/ben/Desktop/diy-bacnet-router`, read AGENTS.md and its required linked documents. Inspect git status, Cargo.toml, the upstream lock and docs/TESTING.md. Follow the repository’s current upstream-check procedure before actual contribution work.

Use this to explore the mechanism. It is deliberately smaller than the assignment.

## Coding challenge

- Write a Rust-produced or hand-authored structured inventory of crate responsibilities, upstream revision and evidence categories.
- Draw router-core, rusty-bacnet-adapter, routerd, upstream stack and OS boundaries.
- Choose one open question that can be investigated without claiming the whole router is complete.

## Experiment

Pick one checked milestone and trace it to concrete evidence. Then pick one open exact-image gate and state what the source tests do not prove.

Write your prediction before running the experiment, then record what changed and why. Use the [capture guide](lab-scripts/wireshark_filters.md) when packets are involved; for offline work, preserve input bytes and actual output instead.

## Acceptance checks

- The checked-out commit and working-tree state are recorded.
- Source and exact-image claims remain separate.
- No dependency pin or product capability is changed as part of the inventory.

## Optional Python companion

Optional data extraction is acceptable; Rust remains the language of the contribution.

## Stretch and reflection

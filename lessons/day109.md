## Concept

HTTP has message semantics above its transport; JSON is a representation, not a transport boundary. A maintained client library should handle real HTTP framing and body limits. TLS authenticates/encrypts according to configured trust and identity, while a WebSocket adds its own lifecycle after upgrade. The router management API is separate from BACnet forwarding. HTTPS elsewhere does not mean the appliance’s current listener implements TLS.

## Tiny example

Use a bounded Rust HTTP client to query the actual documented read-only status endpoint. For TLS, use a separate controlled HTTPS endpoint with a trusted lab certificate and hostname; do not disable certificate checks to force success.

Use this to explore the mechanism. It is deliberately smaller than the assignment.

## Coding challenge

- Implement a Rust status client with connect/overall timeout and a maximum response-body size, using a maintained HTTP library.
- Compare valid TLS trust/hostname with an intentionally wrong hostname or untrusted certificate on the controlled endpoint.
- Study or test a slow management/WebSocket consumer and verify that aggregate updates remain bounded; use the repo-supported instrumentation for forwarding effects.

## Experiment

Compare clear HTTP and TLS captures. Payload visibility differs: following a TLS stream alone does not decrypt it. Decryption requires authorized session secrets and supported capture conditions.

Write your prediction before running the experiment, then record what changed and why. Use the [capture guide](lab-scripts/wireshark_filters.md) when packets are involved; for offline work, preserve input bytes and actual output instead.

## Acceptance checks

- HTTP status, JSON parse errors and TLS failures are distinct.
- The client validates certificate identity rather than accepting every certificate.
- Management responsiveness is not used as the sole proof of healthy data-plane forwarding.

## Concept

MS/TP frames have a preamble, type, destination, source, length and header CRC; data-bearing frames also carry data and its CRC under the applicable frame rules. A preamble-like byte sequence may appear in data or noise. Bounds and CRC help determine whether a candidate is valid. Extended frame forms need separate verified support; do not silently apply a classic-frame parser to everything.

## Tiny example

Use pinned upstream MS/TP frame tests as independent fixtures and record the exact commit/test path. If a capture export is used, identify its serial encapsulation; Ethernet tcpdump does not observe raw RS-485 bytes.

Use this to explore the mechanism. It is deliberately smaller than the assignment.

## Coding challenge

- Write a Rust offline classic-frame inspector for a declared set of frame types, using authoritative CRC vectors and bounded payload length.
- Report header CRC and data CRC separately and recognize no-data frame cases.
- Implement a bounded resynchronization policy after noise/corruption, with counts for skipped bytes and rejected candidates.

## Experiment

Concatenate valid frames with noise, a corrupted header and a truncated tail. Verify that later valid frames can be found without accepting every preamble-like sequence.

Write your prediction before running the experiment, then record what changed and why. Use the [capture guide](lab-scripts/wireshark_filters.md) when packets are involved; for offline work, preserve input bytes and actual output instead.

## Acceptance checks

- Known-answer CRC checks are independent of the encoder under test.
- Unsupported extended forms are reported.
- No loop scans beyond the input or allocates from unchecked length.

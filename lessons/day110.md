# Day 110 — Choose one contribution with a clear owner

[Previous: Day 109](day109.md) · [Course index](INDEX.md) · [Lab guide](LAB_GUIDE.md) · [Next: Day 111](day111.md)

**Week 16 · 45–90 minutes.** Prerequisites: Days 1–109, or equivalent skills. Reuse your earlier work rather than start every tool again.

## Goal

Turn one observed problem into a reviewable Rust change proposal.

## Before you start

Read-only repository study first; software lab and optional isolated Pi/RS-485 bench. Follow the destination repository contract before edits. Follow [workspace and evidence conventions](LAB_GUIDE.md). Save today's work as `student-work/day110/` or in your own learning repository. Record the toolchain; commands and dependency behavior may differ across OS releases. Complete the baseline before the stretch.

## Concept

A useful contribution starts with a concrete failing behavior and a bounded acceptance criterion. Protocol-codec/state-machine bugs may belong upstream; appliance policy and integration belong in the router repository. Moving stack internals into the adapter to avoid an API mismatch creates ownership confusion. A contribution can also be a missing regression test or a reproducible diagnostic improvement if evidence supports it.

## Tiny example

Write a short issue-shaped note: trigger, expected behavior, observed behavior, reproduction, likely owner, and completion check. Name the smallest scenario that demonstrates the problem.

Use this to explore the mechanism. It is deliberately smaller than the assignment.

## Coding challenge

- Select one change supported by Day 108 evidence: a regression test, shutdown fix, diagnostic correction or reproducible lab improvement.
- Read all applicable repo instructions before editing and preserve unrelated working-tree changes.
- Add a failing test or reproducible acceptance check; document where a hardware prerequisite prevents automated reproduction.

## Experiment

Have the proposed acceptance check fail for the original behavior. If it already passes, refine the problem statement instead of making an unrelated change.

Write your prediction before running the experiment, then record what changed and why. Use the [capture guide](lab-scripts/wireshark_filters.md) when packets are involved; for offline work, preserve input bytes and actual output instead.

## Acceptance checks

- The scope can be explained in one paragraph.
- Repository ownership is justified.
- The change does not silently alter upstream pins or broaden capability claims.

## Optional Python companion

Optional peer fixture only. The core implementation/test remains Rust where applicable.

## Stretch and reflection

What unrelated improvement should be explicitly deferred to keep this contribution reviewable?

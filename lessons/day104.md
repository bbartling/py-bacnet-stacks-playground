Dedicated Pi lab or the explicitly labeled VM/offline alternative. Hardware results must come from the actual hardware. Follow [workspace and evidence conventions](LAB_GUIDE.md). Complete the baseline before the stretch.

## Concept

Passive decode establishes that bytes and timing are interpretable before a new station transmits. A controlled join adds MAC uniqueness, framing, adapter ownership and token-state checks. Evidence is specific to baud, adapters, topology and software revision. A passing test on two simulated stations does not automatically extend to a mixed real-controller trunk or a different baud.

## Tiny example

Read the current destination repository hardware guide, testing ledger and hold note before choosing a gate. The course does not override its 38400 shared-trunk hold or authorize attaching to an occupied control network.

Use this to explore the mechanism. It is deliberately smaller than the assignment.

## Coding challenge

- Write a Rust or data-file preflight report for a separate bench: paths, station MACs, Max_Master, Max_Info_Frames, baud and network numbers.
- Run the repository-supported passive mode first, then only the documented bounded join/qualification mode on your isolated bench.
- Record token, CRC, timeout and stop/reopen evidence. Stop on duplicate MAC, token storm or rising errors.

## Experiment

Compare passive-only and controlled-join observations. If hardware is unavailable, analyze recorded evidence and mark every physical gate not run.

Write your prediction before running the experiment, then record what changed and why. Use the [capture guide](lab-scripts/wireshark_filters.md) when packets are involved; for offline work, preserve input bytes and actual output instead.

## Acceptance checks

- Passive and active evidence are separate.
- The exact pinned revision and topology are recorded.
- Hardware failure is not relabeled as a software pass or hidden by raising timeouts without explanation.

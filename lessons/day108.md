## Goal

Run an existing software routing test before proposing a change.

## Before you start

Read-only repository study first; software lab and optional isolated Pi/RS-485 bench. Follow the destination repository contract before edits. Follow [workspace and evidence conventions](LAB_GUIDE.md). Save today's work as `student-work/day108/` or in your own learning repository. Record the toolchain; commands and dependency behavior may differ across OS releases. Complete the baseline before the stretch.

## Concept

A baseline tells you whether a failure was already present. Reproduction needs the exact command, config, revision and environment; passing a related unit test is not equivalent to reproducing a two-interface path. Keep faults isolated and reversible. A failing hardware prerequisite should not be “fixed” by bypassing the gate or synthesizing success counters.

## Tiny example

Locate the repository’s current dual-B/IP test and runbook. Read its setup/cleanup before execution. Use its documented flags at the checked-out revision; this course deliberately does not invent a stable command for an evolving internal harness.

Use this to explore the mechanism. It is deliberately smaller than the assignment.

## Coding challenge

- Reproduce one applicable software gate in the isolated topology and retain its unmodified result.
- Introduce one controlled fault such as an unreachable destination or stopped peer using the documented harness.
- Write a Rust regression test or a reproducible issue note that captures the observable discrepancy, if any.

## Experiment

Compare baseline and fault captures on both sides. Identify the earliest point where expected behavior diverges, rather than assuming every timeout is MS/TP timing.

Write your prediction before running the experiment, then record what changed and why. Use the [capture guide](lab-scripts/wireshark_filters.md) when packets are involved; for offline work, preserve input bytes and actual output instead.

## Acceptance checks

- Baseline and fault use recorded configurations.
- The fault changes one declared variable.
- A pre-existing failure is separated from a regression introduced by your work.
